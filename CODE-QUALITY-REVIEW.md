# Code Quality Review

An evidence-based self-assessment of the codebase against the principles AGENTS.md commits to — SOLID, low coupling, high testability — plus test coverage, scalability, and maintainability. Written by Claude Code at the user's request; every claim below is backed by a command or a file/line reference, not a general impression, so it can be independently re-checked. See [AGENTS.md](AGENTS.md) for the principles being measured against, and [README.md](README.md#testing-strategy--rationale) for the testing strategy this review measures the coverage of rather than re-describes.

## Methodology

- **Coupling/dependency-direction**: `grep`-based checks for which layers import which (e.g. does anything outside `src/server/repositories/` import the generated Prisma client; does anything in `src/server/repositories/` or `src/server/auth/` import from `src/server/services/`).
- **Test coverage**: `node --experimental-vm-modules node_modules/.bin/jest --selectProjects unit integration frontend-unit frontend-integration --coverage --collectCoverageFrom='src/**/*.{ts,tsx}'` — a real instrumented run, not an estimate. This necessarily excludes the Cypress e2e suite (15 tests), which isn't instrumented for coverage here, so the real combined coverage (including `proxy.ts`, page components, and full browser flows that only Cypress exercises) is higher than the numbers below in practice — they measure the Jest suites only.
- **Duplication**: `grep` for repeated literals/function bodies across `src/`, cross-checked by reading the matched files.
- **File size / cohesion**: `wc -l` across hand-written source files (excluding `src/generated/prisma/`, which is Prisma-generated and not hand-maintained).

## SOLID

- **Single Responsibility — mostly good, one component growing multiple concerns.** The repository/service/route split keeps each layer to one job (`ProductRepository` only talks to Prisma, `ProductService` only holds business rules, the route handler only translates HTTP ↔ service calls — see `src/app/api/admin/products/[id]/route.ts`). The one place SRP is stretched is [`product-editor-form.tsx`](src/components/admin/product-editor-form.tsx) (298 lines, the largest hand-written file in the project): it now owns field-edit state, character-limit validation, the save mutation, and the AI-suggestion preview/apply/discard flow all in one component. Nothing is currently broken by this, but it's the component most likely to become hard to follow if another feature is bolted onto the editor.
- **Open/Closed — good, demonstrated twice.** `LlmProvider` (mock vs. OpenAI) and `ShopifyTokenProvider` (static token vs. client-credentials) are both interfaces with two swappable implementations selected at runtime (`resolveProvider()`, `resolveShopifyClient()`) without the call sites (`SuggestionService`, `ShopifyAdminApiClient`) needing to change when a new implementation was added — literally exercised in practice when the client-credentials provider was added after the static-token one already existed and shipped, with zero changes to the class that consumes `ShopifyTokenProvider`.
- **Liskov Substitution — holds, narrowly scoped interfaces.** Every provider/repository interface (`ShopifyClient`, `ShopifyTokenProvider`, `LlmProvider`, `ProductRepository`, `AdminUserRepository`, `RefreshTokenRepository`) is small and implementation-agnostic — a fake satisfying the interface's shape is accepted everywhere a real implementation is (this is exactly what the unit test suite relies on), so no implementation needs to violate or narrow the contract to fit.
- **Interface Segregation — good.** No interface in the codebase forces an implementer to support methods it doesn't need (e.g. `ShopifyTokenProvider` is just `getAccessToken()`; `LlmProvider` is just `generate()` + a `mocked` flag). No "fat" service interfaces were found.
- **Dependency Inversion — good, consistently applied, with one deliberate, documented exception.** Every service/repository takes its dependencies as constructor parameters defaulting to the real singleton (`constructor(private readonly products: ProductRepository = productRepository)`), which is what makes the entire unit-test suite possible without a mocking framework. The one exception is `src/proxy.ts` using `fetch` directly instead of the shared axios instance — documented in AGENTS.md's tech-stack table as an Edge-runtime constraint (no Node `http`/`net` modules available there), not an oversight.

## Test coverage (measured, Jest suites only)

| Scope | Statements | Branches | Functions | Lines |
| --- | --- | --- | --- | --- |
| `src/**` (excl. `src/generated/prisma`, `src/components/ui`) | 68.27% | 70.42% | 68.71% | 72.83% |

This is a real number from an instrumented run (137 Jest tests: 84 unit + 25 integration + 28 frontend), not the Cypress-covered total — see Methodology. **Updated after this review's initial pass**: the two live-network clients called out below as a gap were the direct trigger for adding `tests/unit/openai-provider.test.ts` and `tests/unit/shopify-client.test.ts` — see the AI-WORKLOG.md entry for that follow-up. Breaking down where the remaining gaps concentrate:

- **Near-total to full coverage** (95–100%): the entire `src/server/services/` and `src/server/repositories/` layers, `src/lib/validation/`, `src/server/auth/`, `product-editor-form.tsx`, `shopify-import-form.tsx`, and now `openai-provider.ts` and `shopify-client.ts` as well — i.e. exactly the framework-free business logic and DI-friendly code the testability principle targets is, in fact, thoroughly tested. Both `OpenAiProvider` and `ShopifyAdminApiClient` gained an injectable `http: AxiosInstance` constructor parameter (mirroring `ClientCredentialsTokenProvider`'s existing pattern) specifically so their request-building, status-code handling, and response-shape validation could be unit-tested against a fake instead of `jest.mock` or a live call.
- **What's still not covered, and why that's a conscious remaining gap, not an oversight**: unit tests now exercise these two classes' logic against a fake HTTP client, but nothing automated exercises the *actual* network call — the real request reaching `api.openai.com` / `<store>.myshopify.com` and getting a real response back. That's still only verified by the manual live checks recorded in AI-WORKLOG.md (a real Shopify import, a real OpenAI suggestion). A regression in, say, an actually-wrong base URL or a header the fake wouldn't catch could still slip past `npm test` — this is the nature of testing "did we build the right request" vs. "does the right request work," and the second one is inherently an integration/live concern, not something to fake around.
- **Zero coverage in Jest, expected and covered elsewhere**: `proxy.ts`, page components (`page.tsx`/`layout.tsx` under `src/app/`), and layout-only components (`admin-top-bar.tsx`, `site-header.tsx`) show 0% because Jest never renders a full page or runs Edge middleware — that's what the 15 Cypress e2e tests are for (see README's testing-strategy section for exactly which flows they cover). This is an architectural split, not a gap.
- **Small unmeasured surface**: `src/lib/api-client.ts` and `src/lib/authenticated-request.ts` (the browser axios instance and the session-refresh-retry wrapper) show 0% in Jest. The behavior they exist for (a 401 triggers exactly one refresh-and-retry, a second 401 gives up) is exercised indirectly through the frontend-integration tests that mock at a higher level (`jest.mock` on the module boundary), so the retry *policy* is tested, but the actual axios interceptor wiring inside `authenticated-request.ts` itself isn't directly exercised by any test — a real bug in the interceptor registration would only surface manually. Not addressed in this pass, since the user scoped the ask to the LLM/Shopify gap specifically.

## Scalability

- **No pagination anywhere product data is listed.** `ProductRepository.listAll()` (admin) and `.listPublished()` (public catalog) both run an unbounded `findMany` (`src/server/repositories/product-repository.ts`), and both list pages render every row returned. Fine at the current 3-seed-product scale; would need `take`/`cursor` pagination (and a matching UI) before real catalog-sized data.
- **Stateless application tier, but only one instance is ever run.** The access/refresh JWT auth pattern and the Prisma/Postgres-backed repositories mean the Next.js process itself holds no in-memory session state (good — horizontally scalable in principle), but nothing in the Docker Compose / CI setup actually runs more than one `web` replica, and there's no load balancer config to test that assumption against.
- **One in-process cache, correctly scoped.** `ClientCredentialsTokenProvider` caches the Shopify access token in an instance field with a 60s expiry safety margin (`src/server/services/shopify/token-provider.ts`) — correct for a single process, but would cause redundant token fetches (one per instance, not shared) if the app ever ran as multiple replicas. Not a bug at current scale; worth a shared cache (e.g. Redis) if replica count ever exceeds 1.
- **The Shopify/OpenAI integrations have no retry/backoff.** A single failed request (timeout, transient 5xx) surfaces immediately as a user-facing error rather than being retried — a deliberate simplicity trade-off documented nowhere before this review, worth deciding on purpose rather than by omission if these bonus features were to become core functionality.

## Maintainability

- **Documentation-to-code ratio is unusually high for a project this size** (AGENTS.md, README.md, AI-WORKLOG.md, PROMPTS-HISTORY.md, DEVELOPMENT-PLAN.md, this file) — a real maintainability asset: every non-obvious decision (why Zod limits live in one file, why `proxy.ts` can't use axios, why DI was chosen over `jest.mock`) is written down next to the code it explains, not just in commit messages.
- **Naming and error-handling are consistent across services**: every service-layer failure mode is a dedicated `Error` subclass with a `.name` override (11 across the codebase — `ProductNotFoundError`, `ShopifyClientError`, etc.), always caught by `instanceof` at the route-handler boundary and translated to a specific HTTP status. This is boilerplate-heavy per class but very easy to follow and grep for; not flagged as duplication because collapsing it into a factory would trade a small amount of repetition for a real loss of `instanceof`-based clarity at call sites.
- **The known duplications** (see README's "Known limitations" section: the duplicated `truncate()` helper, the near-duplicate inline truncate in `sanitize()`, and the repeated axios response-handling shape across three files) are the main concrete maintainability debt identified in this review — each is small in isolation, but a future change to truncation or error-handling behavior would need to be applied in 2–3 places by hand, with no compiler check that all copies were updated consistently. Flagged for approval, not fixed, per instruction.
- **The generated Prisma client is committed under `src/generated/prisma/`** — normal for this Prisma setup and excluded from all the analysis above, but worth a reader's awareness that ~4,300 of the ~8,600 total lines under `src/` are generated, not hand-written; the real hand-maintained surface is roughly half that.

## Coupling

- **The dependency graph AGENTS.md commits to actually holds, verified directionally, not just described.** `grep`-checked: nothing outside `src/server/repositories/` and `src/server/db/client.ts` imports the generated Prisma client or `PrismaClient` type; nothing in `src/server/repositories/` or `src/server/auth/` imports from `src/server/services/` (no reverse/circular dependency back up the stack).
- **Client/server boundary is respected**, with one deliberate crossing: Next.js Server Components (`src/app/admin/products/page.tsx`, `src/app/page.tsx`, etc.) import `productService` directly rather than calling their own API route over HTTP — a documented, intentional choice (see AI-WORKLOG.md's Phase 4 entry) that avoids a same-process HTTP round-trip, not an accidental layering violation, since these are server-only files that never ship to the browser.
- **The one cross-feature coupling worth naming**: `src/server/services/shopify/mapper.ts` and `suggestion-service.ts` both import `productContentFieldsSchema` from `src/lib/validation/product.ts` to validate their output against the same limits a manual save would enforce — this is *intentional* coupling (the whole point is that Shopify-imported and AI-generated content can't bypass the manual-save rules), not accidental, and is exactly what let the `PRODUCT_CONTENT_LIMITS` refactor land as a single-file change.

## Testability

- **The DI-over-mocking-framework choice pays for itself.** Every one of the 109 backend unit+integration tests injects a fake or a real Postgres instance, never `jest.mock`; the one place `jest.mock` is used at all is the frontend-integration suite, mocking at the HTTP-client module boundary (a defensible, different layer — see README's testing-strategy section). This makes every test's setup explicit and typed, at the cost of writing a small fake object per test file rather than a one-line `jest.mock()` call.
- **The two live-network classes now follow the same DI pattern as everything else.** `ShopifyAdminApiClient` and `OpenAiProvider` initially had no unit tests (see Test coverage above) because their axios calls went through a module-level singleton rather than an injected dependency — the one place in the codebase that pattern hadn't been applied yet. Adding the same optional `http` constructor parameter `ClientCredentialsTokenProvider` already used made both fully unit-testable with a fake, closing that gap without reaching for `jest.mock`. What's left untestable by design is the live network call itself (see Test coverage above) — that's an inherent limit of unit testing, not a testability gap in this codebase's approach.
- **Two real bugs were caught by the test suites themselves, not by inspection** (already documented in README's testing-strategy section: `LogoutButton`'s missing `catch`, and `GET /products/[slug]` returning HTTP 200 instead of 404 for a draft/unknown slug) — concrete evidence the testability investment is doing real work, not just producing a coverage number.

## Summary

| Dimension | Assessment |
| --- | --- |
| SOLID | Consistently applied; one component (`product-editor-form.tsx`) accumulating multiple concerns worth watching |
| Test coverage | 68.27% statements measured (Jest only), up from 61.85% after adding unit tests for the two previously-untested live-network clients; the remaining gap (the actual network call, and the client-side HTTP wrapper) is understood, not accidental |
| Scalability | Fine at current (test-task) scale; no pagination and a per-instance token cache are the two things that would need addressing before real production data/replica volumes |
| Maintainability | High documentation density is a real asset; the three known duplications (see README) are the concrete debt item |
| Coupling | Dependency graph verified to hold in practice, not just on paper; one intentional cross-feature coupling (shared validation schema) is a feature, not a smell |
| Testability | Strong — DI throughout, fakes over mocks, real Postgres for integration, real browser for e2e; the two live-network clients now follow the same DI pattern as everything else, leaving only the actual network call itself untested by design |
